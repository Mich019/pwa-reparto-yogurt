# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Delisy (formerly "Reparto Yogurt"): PWA for delivery drivers (route map, deliveries, flavors, production forecast, reports) plus its backend API. Code, comments, UI text, identifiers and docs are all in **Spanish** — keep new code consistent with that (`clientes`, `pedidos`, `sabores`, `vendedor`, `administrador`…). Requirement IDs like `RF-037`, `M10` in comments/docs refer to the functional spec.

## Commands

Node ≥ 22. Env vars live in `.env` at the repo root (git-ignored); the API and `db/` scripts read it via `--env-file-if-exists=.env` (so `railway run npm run db:migrar` also works without a `.env`).

```bash
npm run dev            # Vite (5173, --host) + API (tsx watch, port 3000) together; Vite proxies /api → :3000
npm run dev:web        # front only
npm run dev:api        # API only (api/_lib/servidor.ts)
npm run build          # tsc --noEmit (front) + vite build → dist/
npm run preview        # serve dist/ — needed to test the service worker, offline mode and push
npm run typecheck:api  # tsc -p api (front tsconfig only includes src/)
npm run test:api       # node:test via tsx, all api/_test/*.test.ts
npm run db:migrar      # create/upgrade Postgres from db/ (-- --demo loads demo data, -- --reiniciar DROPS everything)
npm run db:admin       # create an admin user (-- correo "Nombre" [--empresa "Empresa"]; creates the company if new)
npm run db:plataforma  # create a platform (super admin) account, or move an existing one there (-- correo "Nombre")
npm run db:probar      # read-only check: env vars, DB connection, SSL, schema/migrations state
npm run db:test        # drop and recreate the local API test DB (DATABASE_URL or the tests' default), like CI
npm run db:datos       # test data INSIDE an existing company (-- "Empresa" [--quitar]): sellers @prueba.delisy.test, clients tagged nfc_uid «prueba:N», orders from after the last closed month; --quitar deletes only that (and phones drop it via eliminaciones)
npm run db:vista       # local demo copy (VISTA_URL on localhost only; -- --rehacer): demo + «Delisy Pruebas» data, every account with one known password (see header of db/vista-local.ts)
npm run push:claves    # generate VAPID keys
```

Single test file: `npx tsx --test api/_test/stock.test.ts`. Filter by name: add `--test-name-pattern="reasigna"`.

API tests run against a **real PostgreSQL** (default `postgres://postgres:test@localhost:5432/reparto_yogurt_test`, override with `DATABASE_URL`). Recreate it from time to time with `npm run db:test` (`db/rehacer-pruebas.ts`: localhost only, name must end in `_test`): it grows with every run, and once the first company has thousands of users, queries hit the 30 s `statement_timeout` and tests fail at random (CI always starts clean). Create that DB with `db/01_esquema.sql`, `02_vistas.sql`, `03_datos_iniciales.sql` (no demo data) — see `.github/workflows/server.yml`. There are no front-end tests and no linter.

Demo accounts (with `04_datos_demo.sql` / `--demo`): `admin@yogurt.local`, `vendedor@yogurt.local`. They have no usable password: `npm run db:migrar -- --demo` sets a random temporary one and prints it (it must be changed on first login). The API will not start without `JWT_SECRET` and `AUTH_PEPPER_SECRET` (two different values, `openssl rand -hex 32`; see `.env.example`). The test helpers use their own password in `api/_test/ayuda.ts`.

## Architecture

### Two runtimes, one repo
- **Front** (`src/`): Vite + React 19 + TypeScript + Tailwind 4 (theme tokens in `src/index.css` `@theme`). No router library: `App.tsx` switches between the field-worker PWA (`views/pwa/`, `PwaLayout` with tabs) and the web admin panel (`views/admin/`) based on whether the path/hash starts with `/admin`. Both share the Danelle look (cream canvas, beige cards, Danelle green/yellow, Bricolage Grotesque headings): `App.tsx` wraps the panel in `.tema-admin` and the field-worker PWA in `.tema-admin .tema-campo` (plus `.oscuro` when the account's theme is dark). `views/admin/tema.css` redefines the colour variables and remaps `bg-tinta`, so screens written with the base palette in `src/index.css` pick it up untouched. One exception: the "Nuevo pedido" sheet (`EditorPedido`, class `diseno-original`) keeps the original black-and-white look inside the PWA only, in light mode (`views/pwa/tema-campo.css`, `.tema-campo:not(.oscuro)`, which also recolours the map pins); in dark the map uses OpenFreeMap's `dark` style (`estiloMapa()` in `Mapa.tsx`; `useEstiloDelTema` swaps it live on a theme change and the route layers are re-added on `style.load`). With «Más grande» text (125%) anything measured in px must scale: Configuración's section menu scrolls on its own, `Selector` and `Calendario` size their pop-ups with the root font size, the guides' phone frame is in rem. Keep rules in that file inside Tailwind layers: an unlayered rule would beat `hover:`/`active:` utilities. Dark mode is `.tema-admin.oscuro` in the same file (preference per account: migration 041 `usuarios.tema` claro/oscuro/sistema, `PATCH /me` `tema`, `elegirTema` in `sesion.ts`, copied by `refrescarPerfil` into `src/lib/tema.ts` — a browser that had one chosen passes it to an account still on «sistema» once, `tema-en-cuenta` —, chosen in the panel's Configuración section and in the PWA's Cuenta → Preferencias → Tema; the panel's text size is per account too — migration 042 `usuarios.tamano_texto` normal/grande/mas-grande, `PATCH /me` `tamanoTexto`, `elegirTexto` in `sesion.ts`, inherited once from the browser with `texto-en-cuenta` — while «Menos movimiento» stays per browser; in light mode the canvas can be white, cream or grey, per account and apart from the company brand: migration 040 `usuarios.fondo` (existing accounts kept cream, new ones start white), `PATCH /me` `fondo`, `elegirFondo` in `sesion.ts`, copied by `refrescarPerfil` into `PreferenciasPanel.fondo` (a browser that had chosen one before passes it to the account once, `fondo-en-cuenta`); «Color del fondo» in Configuración → Apariencia and in the PWA's Cuenta → Preferencias, applied for both sides by `useAplicarFondo` in `App.tsx` as `html.fondo-blanco`/`fondo-gris` (redefine `--color-lienzo`/`--color-papel` in `tema.css`; `public/arranque.js` paints the boot screen to match); the order of the panel menu is per account instead — `usuarios.orden_menu`, migration 026, `PATCH /me` `ordenMenu`, cached as `ordenMenu` in `lib/tema.ts` and refreshed by `refrescarPerfil` — applied by `views/admin/menu.ts`: add new panel sections to `PESTANAS` there): use the colour tokens (`bg-papel`, `text-tinta`, `--chip-*`…), never literal hex or `bg-white`, so new screens work in both.
- **API** (`api/`): Fastify 5 on PostgreSQL (`pg`, raw SQL, no ORM), zod validation, JWT + Argon2id. `api/_lib/app.ts` `construirApp({db, config, enviador?})` builds the app and registers every route module (`auth`, `sync/`, `usuarios`, `cartera`, `reportes`, `stock`, `notificaciones`, `admin`, `recuperacion`, `cobranza`, `envases`, `precios`, `cortes`, `empresa`, `plataforma`…). Internal errors (5xx) go to Sentry from the error handler when `SENTRY_DSN` is set (`api/_lib/errores.ts`, hand-rolled envelope, no dependencies; never the request body or the DB `detail`); the browser does the same with `VITE_SENTRY_DSN` in `src/lib/errores.ts` (strips query/fragment, skips network noise). Two entry points wrap it: `api/_lib/servidor.ts` (local dev) and `api/index.ts` (single Vercel serverless function; `vercel.json` rewrites `/api/*` to it). Folders prefixed with `_` are not exposed as Vercel endpoints. The app strips a leading `/api` so routes work both with and without the prefix. API imports use `.js` extensions (NodeNext).
- `api/_lib/config.ts` is the single source of env config (`DATABASE_URL` or `DB_*`; SSL is decided there — Railway's public `*.rlwy.net` host or `?sslmode=require` → encrypted without cert verification unless `DB_SSL_CA`; `sslmode` is stripped from the URL because pg would let it override the `ssl` option; `JWT_SECRET` ≥32 chars, `CORS_ORIGINS`, `VAPID_*`, `ZONA_HORARIA`, `RESEND_API_KEY`…). `db/migrar.ts` reuses it.

### Offline-first data flow (the core concept)
- The phone stores everything in IndexedDB via Dexie (`src/lib/db.ts`, schema versions declared with `db.version(n)`; add a new version when changing stores). Every local change is also appended to the `cola` table.
- `src/lib/sync.ts` pushes the *current state* of each touched record in dependency order (productos → clientes → pedidos → recordatorios) to `POST /sync/push`, then pulls `GET /sync/pull?desde=<cursor>`. Each operation carries its own UUID (idempotent replays) and the server `version` it was edited from.
- Conflict rules live server-side in `api/_lib/sync/aplicar.ts` (closed orders always win; closing beats editing; otherwise latest timestamp with clock-skew correction; delete-vs-edit is rejected). Losers are stored in `operaciones_sync` and shown to the user, never silently dropped. `sync/adaptadores.ts` maps between the phone's shape and DB rows; `sync/esquemas.ts` holds the zod schemas.
- Deletions propagate via the global `eliminaciones` table; portfolio reassignment instead uses `retiros_vendedor` (per-seller removal). Don't conflate the two.
- Sending the queue lives in `src/lib/envio.ts`, shared by the app (`sync.ts`) and the service worker: `src/sw/envio.ts` is bundled separately into `dist/sw-envio.js` (IIFE, `vite.config.ts` plugin) and `public/sw.js` loads it with `importScripts` to push the queue on Background Sync with the app closed (RF-052). It reads a copy of the session that `sesion.ts` mirrors into `db.meta` (`sesion-segundo-plano`); refresh tokens don't rotate, so the SW and the page can both refresh. Logouts without signal are queued (`revocar-pendientes`) and revoked when back online. Page and SW serialize sends with `navigator.locks`.
- **Live updates** (no reload, no "Sincronizando…"/"Actualizando…" banners): migration 029 adds `cambios` (one counter per company and area: `datos` = what sync pulls, `cobranza` = abonos/envases/cortes/cierres/pedidos, `equipo` = accounts, not `ultimo_acceso`), bumped by deferred constraint triggers once per transaction (`fn_marcar_cambio`). `GET /eventos` (`api/_lib/envivo.ts`, server-sent events on the owner pool, filtered by company) polls it every 3 s, re-checks the session (logout cuts it), and closes itself after 240 s so the client reconnects (Vercel limit; `vercel.json` sets `maxDuration` 300). It only says *which area* changed; data still comes through the normal routes. Front `src/lib/enVivo.ts`: the layout (parent) opens one connection per tab with `useConexionEnVivo()` (fetch stream, token in the header; closed while the tab is hidden, and on return every area is notified); screens (children) call `useEnVivo(area, fn)` (callback kept in a ref, debounced) and refetch silently, keeping what they show. `sync.ts` pulls on `datos` (so every Dexie `useLiveQuery` screen updates by itself), `useServidor` (cobranza) refetches on its area, `useEquipo` on `equipo`/`datos`, `useReporte` and `useDiaStock` (Reportes, Producción) and the dashboard on `datos`; sheets with a form (stock carga/producción) only reset their inputs when opened, so a live refresh never overwrites what is being typed; the 60 s polling only runs while not connected. The header shows «En vivo»; background syncs are never announced, only errors and manual taps.
- `src/lib/api.ts`: `API_URL` = `VITE_API_URL` or `/api`; `MODO_SERVIDOR` is true unless `VITE_OFFLINE_SOLO=true`. Without the server, the app works purely local (seeded flavor catalog, no login).

### Roles and security invariants
- **Admin who also delivers** (small companies): no flag, no migration. Server side an admin counts as a seller when they have clients or orders in their name (`vende()` in `api/_lib/vende.ts`, used by cortes, stock and the `/mi-meta` place); `/sync/pull` gives everyone their own `stock_diario`. Where they log in decides what they see: in the PWA (`PwaLayout` calls `fijarReparto`, `src/lib/reparto.ts`) they work as a seller — Ruta, Clientes, Stock, Por cobrar and «Qué hacer hoy» chips show only their portfolio plus unassigned clients (`esMio`), new clients/orders get `vendedorId` = them (`conservarDelServidor` in `db.ts`), Cuenta shows Mi día (`reparte()`); in `/admin` they get the full panel (the shared Dexie is never narrowed). The Ruta chips (`AlertasRuta.tsx`): urgent first, low stock, clients due a visit without an order (opens `VisitasSinPedido.tsx`: one `wa.me` link per client). WhatsApp messages are editable per account (`components/Mensajes.tsx`: `useMensaje`/`EditorMensaje`/`BotonWhatsApp`/`llenar`/`MandarATodos`; migration 035 `usuarios.mensajes` jsonb, `PATCH /me` `mensajes` — null resets one —, copied by `refrescarPerfil` into `db.meta` `mensaje:<tipo>` for offline use; «Mandar a todos» in Por cobrar opens one chat per tap, browsers block several at once; `visita` with `{nombre}` — also used by the bell reminders — `cobro` with `{nombre}`/`{saldo}` and `limite` (debtors over their limit) with `{limite}` too, a button per debtor in Por cobrar, PWA and panel); no WhatsApp API, corte to hand in, unsynced changes. Such an admin sets their own monthly goal in Cuenta → Preferencias (`PATCH /mi-meta`, admin only; sellers' goals stay in the team form). Flavors marked unavailable («Dejar de producir» in the flavor sheet when nothing sold in 30 days) are no longer estimated by the forecast (already-ordered amounts still count).
- `administrador` vs `vendedor`. Sellers only see their own portfolio and **never receive costs/margins** — the server omits them; reports, stock capture and team management are admin-only routes.
- Own profile: `PATCH /me` (name, phone, `foto`; never email or role), `GET /me/sesiones` + `POST /me/sesiones/cerrar` (never the current one). The profile photo (`usuarios.foto`, migration 012) is a 256 px WEBP data URL (JPEG fallback) framed by the user in a crop sheet (`EncuadreFoto` in `components/Avatar.tsx`, drawing in `src/lib/imagen.ts`); it is not in the login response — `refrescarPerfil()` loads it into the session. Show people with `components/Avatar.tsx`.
- Every authenticated request re-checks `sesiones` + `usuarios.activo` in the DB (so logout/deactivation is immediate). `debe_cambiar_password` blocks everything except password change.
- Rate limits (`@fastify/rate-limit`, per route) count in Postgres (`api/_lib/limites.ts`, UNLOGGED table `limites_peticion`, migration 017), not in memory: Vercel runs several instances. Login lockout (`intentos_login`, `registrarIntento` in `auth.ts`) is per IP + account, plus a cross-IP cap per account (`maxIntentosCuenta`) that spares IPs that logged in successfully recently (`diasIpConocida`), so an attacker can't lock the owner out.
- Copy secrets (temporary passwords, invitation links, 2FA keys, backup codes) with `copiarDelicado` (`src/lib/portapapeles.ts`), which clears the clipboard after 60 s.
- Inside transactions the API sets `SET LOCAL app.id_usuario` for DB-trigger auditing, and `SET LOCAL app.permitir_correccion = 'on'` to edit a closed order. Admin-count changes are serialized with `pg_advisory_xact_lock`.

### Multi-company (tenancy)
- One shared DB; every business table has `id_empresa` (table `empresas`), composite FKs `*_misma_empresa`, and RLS policy `por_empresa` for role `reparto_app` (PostgreSQL 15+). `api/_lib/db.ts`: an AsyncLocalStorage scope per request (`conAlcance` in `app.ts`), `fijarEmpresa` when the session is validated, then `porEmpresa(pool)` and `tx()` run each query/transaction as `SET LOCAL ROLE reparto_app` + `app.id_empresa`. Code before the company is known (login, refresh, password recovery) runs as the DB owner and sees everything — filter explicitly there.
- `id_empresa` defaults to `current_setting('app.id_empresa')`, so INSERTs don't name it. Views are `security_invoker`; trigger functions take the company from the row. A suspended company (`empresas.activa = false`) gets 403 `EMPRESA_SUSPENDIDA` on login/refresh/every request.
- Self-signup (`api/_lib/registro.ts`, front `views/registro/`): `/registro/codigo` emails a 6-digit code (no account enumeration: an existing address gets a "you already have an account" email instead), `/registro/verificar` returns a signed 24 h `comprobante`, `/registro/empresa` creates company + admin + products + invitations in one owner transaction (no company in scope yet; `set_config('app.id_empresa')` gives the rows their owner). Until the flexible catalog exists, each product × variant × container becomes a `productos` row (ml/g → L/kg in `presentacion_litros`, container name in `descripcion`). Invitations: `/invitacion#<token>` (fragment, HMAC stored), `/invitacion/consultar|aceptar`; admins invite more with `POST /invitaciones`. Links use `APP_URL`.
- Billing (`api/_lib/suscripcion.ts`, `mercadopago.ts`; front `lib/suscripcion.ts`, `views/admin/Suscripcion.tsx`): a company has access if `exenta` (companies that existed before billing, and the first one of an install), still in its free trial (`prueba_hasta`, `PRUEBA_DIAS`) or its Mercado Pago subscription (`/preapproval`) is `authorized`. Without access, `autenticar` answers 402 `SUSCRIPCION_VENCIDA` except for routes guarded with `passwordPendiente`/`sinCobro` (session, `/suscripcion*`); nothing is deleted. Status comes from MP's API on the signed webhook (`POST /mercadopago/webhook`) and on return from checkout (`?suscripcion=volver` → `GET /suscripcion?actualizar=1`). Without `MP_ACCESS_TOKEN` + `MP_PRECIO_MENSUAL` nobody can subscribe but the app works; tests inject a fake `mercadoPago` client.
- Per-company brand (`api/_lib/empresa.ts` GET/PATCH `/empresa`; front `lib/marca.ts`, `views/admin/MarcaEmpresa.tsx`): name, logo (data URL), color, and (migration 013) `lema` + `contacto` printed in the PDF header/footer. Logos are checked and fixed in the browser by `src/lib/logo.ts` (`revisarLogo`: flat background, resolution, shape, too light/dark, main colours offered as brand colour; `prepararLogo`: optional background removal by flood fill from the edges, trims margins, ≤512 px WEBP; SVG kept as is), used by Marca and the signup. `App.tsx` sets `--color-marca`/`--color-marca-oscuro` from the company color (darkened until white text reaches 4.5:1). Use `LogoEmpresa`/`AveEmpresa`/`Frasco` from `views/admin/marca.tsx`: a company without a logo shows its initial and name (no other company's logo, ever). PDFs take the name/color from `marcaActual()`; the Marca screen shows, live and unsaved, the first page of a sales report drawn by the real PDF code with the draft brand and grey skeleton blocks instead of data (`hojaDeMuestra` in `reportePdf.ts`, its SVG twin). The logo goes on the PDF cover as a JPEG XObject (`Documento.imagen`; `imagenParaPdf` rasterizes any format onto white): call `prepararLogoPdf()` before building a report, since PDF generation is synchronous. The brand is cached in localStorage so it shows offline and on the next login screen.
- Flexible catalog (migration 010): `productos.unidad` (L default, kg, pz…) and `envase` (a `TIPOS_ENVASE` key, null = sold loose), both fixed at creation like `presentacion_litros`, which now means content per container *in that unit*. On the wire the old names stay (`litros` = quantity in the product's unit, `precio_litro` = price per unit) so phones and queued operations keep working; show them through `src/lib/unidades.ts` (`cantidadEnPantalla`, `precioEnPantalla`, `totalPorUnidad`…), never hard-coded "L". Totals across products are summed per unit, never liters with kilos: phone side with `totalPorUnidad`/`sumaPorUnidad`/`textoPorUnidad`; server side reports, `/admin/stats` and the client book return `porUnidad` (`{ L: 60, kg: 10 }`) plus `unidades` (from `api/_lib/unidades.ts`), and Excel gets one quantity column per unit. With a single unit everything reads as before.
- Cobranza (migrations 018–022; panel section `views/admin/Cobranza.tsx`, shown as «Finanzas» (id still `cobranza`: saved menu order, `?ir=`, help; shortcut «g f») with tabs Por cobrar / Envases / Cortes del día / Cierre de mes, each explained under the title; above them `FranjaFinanzas` (four figures between two rules, each opens its tab: owed, today's cash still to confirm — handed-in amount for pending cortes —, containers lent, the month's sales from `GET /cierres/:mes`) and «Cortes del día» shows a count of today's pending cortes plus confirmed ones that no longer match (`useCortesPorAtender`, fetched once in `AdminLayout` and passed down, refetched by «Cortes del día» after any change; the same count shows beside «Finanzas» in both navs, `NumeritoCortes`); the month's sales figure compares month-to-date with the same stretch of last month from Dexie (delivered orders); the Cortes tab offers «Confirmar los N que cuadran» (pending, difference 0, confirmed one by one) when two or more match; the welcome tour has a step on those tabs (`data-seccion="finanzas-pestanas"`, `PasoGuia.abrir`); front API in `src/lib/cobranza.ts`). All of it is **online-only** (plain API calls, not in the sync queue) except two things that travel with sync: the `CREDITO` payment method ("Fiado") and the per-client special prices.
  - **Fiado** (`api/_lib/cobranza.ts`): a delivered order with `metodo_pago = 'credito'` adds to what the client owes; `abonos` lower it (never deleted: `POST /cobranza/abonos/:id/anular` with a reason). Balance = sold on credit − abonos not annulled; "since" is the oldest uncovered order (abonos pay the oldest first). Admin sees every debtor, a seller only their portfolio (`clienteVisible`). Abonos are locked to the balance with a row lock on the client. `Falla`/`comoFalla` map DB errors to 4xx.
  - **Envases retornables** (`api/_lib/envases.ts`): `productos.retornable`; balance per client and product = delivered − `envases_recogidos` (not annulled). Editable in the flavor form after creation. Whether the company uses them at all is `empresas.control_retornables` (asked at signup; PATCH `/empresa` `controlRetornables`, «Envases» in the panel's Preferencias; migration 044 turned it on for companies that already had a returnable product): off hides Finanzas → Envases, its strip figure, the client sheet's envases and the flavor form's «Envase retornable» (`useConEnvases` in `lib/marca.ts`); product marks are kept.
  - **Precio especial por cliente** (`api/_lib/precios.ts`, admin only): `precios_cliente` stores it per container like `detalle_pedido.precio_unitario`; `fn_detalle_precios` uses it for new items and `clienteWire.precios` carries it to the phone (`EditorPedido` applies it). Editing bumps `clientes.actualizado_en` so phones pull it.
  - **Límite de fiado por cliente** (migration 036 `clientes.limite_fiado`, admin only: `PUT /clientes/:id/limite-fiado` in `precios.ts`, `components/LimiteFiado.tsx` in the client sheet): travels to the phone as `clienteWire.limiteFiado` (what the phone pushes is ignored); choosing «Fiado» at delivery shows `AvisoLimiteFiado` in Ruta (current balance from `/cobranza/clientes/:id` when online, just the limit offline). Clients without their own limit use the company's (`empresas.limite_fiado`, same migration; PATCH `/empresa` `limiteFiado`, null clears; «Fiado» in the panel's Preferencias), on the phone through `useMarca()`. `Deudor.limite` is the effective one and `pasoSuLimite` marks debtors over it in red in Por cobrar (panel and phone); the `fiado_atrasado` notice says who passed it. The panel's Por cobrar also has «Pasaron su límite» (shown when someone did) and its Excel adds each limit and whether it was passed; the daily/weekly email counts clients over their limit at the end of the period (`pasaronLimite`). The phone's Por cobrar (`components/PorCobrar.tsx`) offers Todos / «Pasaron su límite»; the client sheet draws a bar of debt against the limit (`BarraLimite` in `CuentaDelCliente`, amber from 80%, red over it); the Clientes Excel has the effective limit. `GET /cobranza/clientes/:id` returns `limite`, so «Abonar» (`HojaAbono`) says what would remain and against the limit; the seller's Ruta marks clients over their limit (a red triangle in the active card and in «Siguientes paradas», from `/cobranza` when online); at delivery `AvisoLimiteFiado` also says how much can still be sold on credit; when a seller's synced credit sale leaves the client over the limit, the other active admins get `fiado_sobre_limite` (switchable, `avisarFiadoDeMas` in `sync/adaptadores.ts`, opens `?ir=cobrar`). The limit sheet (`HojaLimite`) suggests one (`limiteSugerido`: two weeks of the client's deliveries of the last 90 days, rounded up to $50, halved if they owe since more than 30 days); Clientes → «Más» → «Límite sugerido para todos» (`HojaLimitesSugeridos`, admin) puts it on every active client without their own limit at once (`PUT /clientes/limites-fiado`). The seller's sheet in Vendedores says how many credit sales this month left a client over the limit (`GET /cobranza/fiado-de-mas`, admin; uses today's limit). Optional block (migration 037 `empresas.codigo_fiado`, PATCH `/empresa` `codigoFiado` 4–8 digits, null clears; «Código para fiar de más» in Preferencias → Fiado): stored and sent to every phone as `sal:sha256(sal:código)`, and `AvisoLimiteFiado` disables «Pedido Realizado» (`onPermitir`) for a credit sale over the limit until the admin's code is typed (`codigoFiadoCorrecto`, works offline). It is an everyday brake, not a password: a 4–8 digit code can be brute-forced from the phone's copy. Debtors over their limit get their own WhatsApp message (`limite`, with `{limite}`; `textoCobro` in `Mensajes.tsx` picks it in Por cobrar, phone and panel). The home's «Pedidos recientes» has «Buscar pedidos» (`views/admin/BuscarPedidos.tsx`: every order in Dexie by client or flavor, filtered by state; tapping one opens its client's sheet through `abrirCliente` in `Clientes.tsx`). «?» shows the panel's shortcuts and «g» + a letter jumps to a section (`AtajosTeclado`, list `IR_A`, same `teclaLibre` rule). «Buscar pedidos» also filters by payment method (only delivered orders have one). «Buscar pedidos» also matches the seller's name (`useEquipo`) and the date (`fechaBuscable`: hoy/ayer/mañana, weekday, day, month). It sums what it found (and what of that was delivered) and downloads it as Excel with `src/lib/xlsx.ts` (one-sheet XLSX built in the browser: stored zip + CRC-32, text as inlineStr so nothing runs as a formula; the server's multi-sheet Excel stays in `api/_lib/exportar.ts`). The panel menu's titles show each section's «g» shortcut (`atajoDe`). Cobranza → Por cobrar has its own header search (client or seller) and «Bajar a Excel» (what the search left, `src/lib/xlsx.ts`); so do Clientes (with each client's fiado balance and envases from `/cobranza` + `/envases` when online, columns left out otherwise) and Vendedores (with the month's sales and what is left to the goal, from `GET /cierres/:mes`, when online), in their «Más». `vidrio` (`components/ui.tsx`) is the shared frosted glass for sheets, «Más», `Selector`, `Calendario` and `PanelSabor`. «Buscar pedidos» also highlights matches in the date.
- «Dejaron de comprar» = active client that already bought, has no pending order and whose last delivery is more than 30 days old (same rule in Clientes — chip + «Escribirles» through `VisitasSinPedido` with a `titulo` —, the Resumen's «Qué hacer hoy» via `verSinComprar()`, and the seller's sheet in Vendedores). The client sheet shows the real buying rhythm (`cadaCuanto`/`RitmoDeCompra` in `Clientes.tsx`, also an Excel column) and «Repetir el último». WhatsApp message `camino` («Voy en camino» on the Ruta stop card, edited in Cuenta); the client sheet sends the fiado statement (`textoEstadoCuenta` in `lib/comprobante.ts`); «¡Ruta terminada!» shows cash/transfer/fiado (`ComoTePagaron`) and shares it.
- Long lists (clients, team, QR selection, portfolio reassignment, platform companies) are paged with `usePaginas` (`components/Paginas.tsx`), never rendered whole; pass what defines the list (search, filter) as `reinicio` so it goes back to page 1.
- Producción → Pronóstico (`views/pwa/Pronostico.tsx`, `pronosticoSemanal(…, desde, dias)` in `lib/pronostico.ts`): horizon Mañana / 3 días / Semana (localStorage `delisy:horizonte`); two columns on large screens: «Por sabor» rows (name | bar | total) and a sticky summary aside (total, ya pedido/estimado bar, ya anotado, «Anotar lo producido», «Imprimir hoja», «¿Qué tan atinado es?»); «Día por día» is a table of days × flavors tinted by amount (`cantidadesPorDia`), also printed on the kitchen sheet with 3 días/Semana (`hojaProduccionPdf(…, porDia)`); each flavor's bar in its own colour, solid = already ordered (pending orders in range), striped (`.relleno-estimado`) = estimated from clients due a visit without an order; the two totals double as the legend, and «¿Ya lo produjiste?» jumps to Stock del día (`onRegistrar`). With the server it subtracts what is already recorded in Stock del día for those days (`GET /stock/producido?desde&hasta`, admin, ≤ 31 days; `useProducido` in `lib/stock.ts`) and says what is missing per flavor; «Imprimir hoja» draws a one-page kitchen sheet (`hojaProduccionPdf`); «¿Qué tan atinado es?» (`aciertoPronostico`) redoes each of the last 14 days' forecast with what was known the day before (history + that day's orders created before midnight, by `Pedido.creado`) and compares it with what was delivered, per unit; its «Corregir el pronóstico según esto» (localStorage `delisy:corregir-pronostico`) scales each unit by delivered/estimated when the bias is ≥ 8%, never below what is already ordered. With 3 días/Semana, «Día por día» lists what goes out each day (`pronosticoSemanal(...).dias`). **Production reminder** (`api/_lib/produccion.ts`, `avisarProduccionPendiente`): from `HORA_AVISO_PRODUCCION` (default 18, «no» = off; company timezone), if tomorrow's pending orders of a flavor exceed what is recorded in `produccion_diaria` for tomorrow, active admins get `produccion_pendiente` (switchable, once per company and day via `datos.fecha`, opens `/admin?ir=produccion`); only confirmed orders count (the estimate lives on the phone). Woken like urgentes (live connection + `/cron/urgentes`); the test config turns it off (`horaAvisoProduccion: null` in `ayuda.ts`) so it doesn't notify the whole test DB. Tests never `set_config('app.id_empresa', …, false)` on the shared pool (it leaks to other tests on that connection): name `id_empresa` in the INSERT.
- Reportes (`views/pwa/Reportes.tsx`): for Día/Semana/Mes, «Últimos 14 días / 8 semanas / 12 meses» (`Tendencia`, a second `useReporte` around the period, drawn with the panel's `BarrasPeriodo` with the viewed period in gold; tapping a bar goes to that period via `onElegir`; measure switch Ingresos/Utilidad/<unidad>/Pedidos, the unit only with a single one), always shown even without sales; «Comparar con hace un año» (localStorage `delisy:comparar-anio`) adds a thin grey bar per period from the same period a year before (364 days for days/weeks, keeps the weekday; 12 months for months) via `BarrasPeriodo`'s `previo`, aligned by position, with its value and % in the bubble and table. Each seller row opens `HojaVendedor`: their figures for the period, the month's goal progress (`GET /reportes/ventas?vendedor=<id>` — optional filter, export ignores it — counted like `/mi-meta`, with the pace mark) and the same `Tendencia` filtered to them. With sales, «Cómo te pagaron» and «De qué se vendió más» (`BarraSegmentada`, legend with amount and %). «Fiado» (`FiadoDelPeriodo`) compares what was sold on credit in the period with the abonos collected (`Reporte.abonos`, not annulled, by their date, filtered by seller like the rest) and says whether pending credit grew or dropped; with more than one seller, «Quién cobra mejor» lists each one's credit sales vs. the abonos they recorded (`Reporte.fiadoPorVendedor`, sorted by how much each lowered what is pending).
- Stock-low and unsynced-sales alerts are computed on the phone (`src/lib/alertas.ts`); server-generated notices (urgent order, route changes) are created in the same transaction as the change and delivered in `pull` and by Web Push (`api/_lib/push.ts`, best effort; tests inject a fake `enviador`).
- "Today" server-side comes from the company: `empresas.zona_horaria` (edited at Configuración → Marca, `ZonaEmpresa.tsx`; read through `zonaDeEmpresa` in `api/_lib/fechas.ts`, cached 60 s, `olvidarZona` after a change). `ZONA_HORARIA` (default `America/Mexico_City`) is only the fallback and should match the delivery phones' timezone.

### Deployment
- Production target: app + API on Vercel, PostgreSQL on Railway — step by step in `docs/produccion-railway.md`.
- `vercel.json`: Vite static build + the `api/index.ts` function + a daily cron (`/api/cron/avisos`, needs `CRON_SECRET`; Hobby plan only allows daily). It also sets the app pages' CSP: a new external origin (another OSRM or tile server, `VITE_API_URL` on another domain) must be added to its `connect-src`/`img-src`. `.github/workflows/pages.yml` also deploys `dist/` to GitHub Pages (with `VITE_API_URL` from the repo variable `API_URL`); `server.yml` runs typecheck + API tests (twice, the second over the first run's data, to catch order-dependent tests) on changes to `api/`, `db/` or package files.

Note: some READMEs still refer to an old `server/` folder; the API now lives in `api/`.
